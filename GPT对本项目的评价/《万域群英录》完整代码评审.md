# 《万域群英录》Godot 源码评审

## 一、结论与评审边界

**建议继续开发，保留现有项目，先修正战斗内核并完成一个小而完整的对战版本，不建议推倒重写，也不建议立即扩充大量角色。**

以作者“这些代码是本人纯手写”为前提，本项目足以说明作者已经能够独立实现相互关联的游戏系统，而非仅完成孤立的教程功能。角色继承、Buff 生命周期、元素反应、队伍切换和收益评分 AI 都是有价值的积累。主要短板集中在状态一致性、异步流程控制、对象生命周期、重复数据和边界测试。不能仅凭这份代码推断就业竞争力、商业销量或作者在所有编程领域的能力。

### 检查范围

- 52 个 GDScript 文件，合计 5,203 个物理行；其中空行 585 行、纯注释行 642 行，其他行 3,976 行。行数只说明规模，不是质量评分。
- 23 个 `.tscn` 场景。
- 19 个角色脚本；随机角色池包含 17 个，另外两个明显属于占位或未完成角色。
- `project.godot` 标注 Godot 4.7、GL Compatibility、1280×720。
- 阅读了主要战斗控制、角色基类、AI、Buff 和角色技能实现，检查了项目结构及字面量资源引用。
- 字面量 `res://` 路径及本地 UID 对照扫描未发现缺失；这不等同于成功导入、编译或导出。
- **未在 Godot 中启动或试玩。没有进行性能测量、完整交互复现、Android 验证或商业可行性调研。**
- 本次没有修改原始源码。所有行号对应上传 ZIP 中的这份快照。

### 当前玩法形态

从源码看，这是双方各五名角色、各一名角色站场、可以替换角色的回合制对战原型，包含速度先后手、能量、普攻与四个技能、元素克制、异常状态、Buff、入场效果及 AI。主菜单代码包含双方随机和固定己方队伍对战入口；队伍编辑按钮在场景中被隐藏，不能算作已经完成的组队功能。

## 二、应当保留的优点

### 1. 有共用规则与具体角色的分层

`base/character_base.gd` 承担角色通用数据和伤害、状态等方法，各角色脚本扩展具体技能。角色场景也使用继承。虽然基类已经偏重，但方向有利于复用，不应因为发现问题就废弃这套成果。

### 2. Buff 不只是随处修改属性

已有独立的 Buff 基类、管理器、叠层与持续时间机制、施加和移除钩子、回合及伤害事件。下一步应修生命周期和叠加契约，而不是重新发明一个更复杂的框架。

### 3. AI 有实际策略建模

`scripts/ai/fighting_ai.gd` 不只随机选技能：能看到对击杀、治疗溢出、能量紧缺及储备、延迟收益、克制、换人和对手已出现角色的考虑。这说明作者会把玩法规则转化成可计算的选择依据。

缺点是评分目前有副作用、多份技能数据不一致等问题。应先让相同局面能稳定得到相同判断，再调评分权重。

### 4. 系统组合能力比单个特效更值得肯定

角色涉及入场、治疗与换人、物理附加魔法伤害、护盾和攻击转换、延迟收益等组合。价值在于已经尝试让不同规则相互作用，而非只是给同一个攻击函数换数值。

## 三、优先修复项

下述优先级表示建议处理顺序，并非经过完整运行验证后的事故严重级别。
“确定逻辑问题”指能从代码与相关规则直接推出；
“流程风险”指已发现危险路径，但未进行真实输入时序复现；
“扩展隐患”指当前角色配置可能暂未触发。

### P1-01：战斗行动入口缺少统一的合法性与重入检查

**位置**

- `scripts/fighting.gd:345–363`：四个技能按钮入口直接调用角色技能。
- `scripts/fighting.gd:649–666`：是否启用技能按钮只看能量。
- `scripts/fighting.gd:220–225`：动画期间每个物理帧都会调用 `begin_animation()`。
- `scripts/fighting.gd:1190–1202`：该方法等待后重新启用按钮，没有单次运行保护。
- `scripts/fighting.gd:691–719`：回合推进本身含等待，需要一起纳入流程检查。
- `base/character_base.gd:241–263`：基础技能扣能后钳制到零，并不等价于拒绝非法施法。

**判断：高优先级流程风险。**

在一个动画仍未结束时，可能已经创建了多份等待中的 `begin_animation()` 调用。它们醒来后会重新刷新按钮，而刷新逻辑并未同时判断是否己方回合、是否正在换人或是否已经结算完毕。按钮禁用状态不能成为战斗规则的唯一防线。

项目自己的待开发记录也提到了快速点击能放出技能的问题；这里是与该问题相符的源码路径，不是已经复现其全部输入条件。

**建议**

建立单一行动入口，先同步验证战斗状态、行动者、能量、目标，然后才扣费或进入等待；使用明确的战斗状态区分等待玩家、选择目标、结算行动、强制换人、AI 行动、战斗结束。动画只反馈“播放完成”，不能自行决定轮到谁或能否行动。

不要只加一个毫秒级点击冷却。还要正确处理不结束回合的技能、取消选人和死亡替换。

**验收**

连续点击两种技能不会重复扣能或重复推进；敌方行动期间所有玩家输入都被逻辑层拒绝；合法的连续行动技能仍可正常再次发动；取消选择能恢复正确状态。

### P1-02：伤害增减在两层被重复应用，普攻与技能走不同结算路径

**位置**

- `base/character_base.gd:341–364`，特别是第 356 行。
- `base/character_base.gd:366–373`，特别是第 368 行。
- `scripts/character/pvz2_wandousheshou.gd:15–19` 给出实际嵌套调用。
- `base/character_base.gd:265–270` 普攻直接调用受伤及伤害事件。
- `base/character_base.gd:329–332` 发出伤害事件后才乘轮次倍率，结果没有再用于扣血。

**判断：确定逻辑问题。**

`damage()` 已经计算 `damage_reduction` 与 `damage_improve`，`be_and_to_damage()` 又计算一次，而角色技能通常把前者的输出传给后者。

在克制、攻防和轮次倍率均不额外改变结果的假设下：

- 原始伤害 1,000，攻击者只有 100% 增伤：先变成 2,000，再变成 4,000。
- 原始伤害 1,000，目标只有 80% 减伤：先变成 200，再变成 40。

这里不是判断“你的增伤应采用哪一种公式”，而是同一规则被结算两次。潜水僵尸技能实际会给予这类 100% 增伤、80% 减伤数值，因此不只是理论案例。

此外，普攻绕过另一层结算；`to_damage()` 中在事件发出之后改变局部变量，不能反过来修改已经扣除的血量。普攻还计算了两次伤害，第一次受伤可能清除状态，使第二次事件使用不同数值。

**建议**

用唯一伤害结算入口生成结果对象：输入施法者、目标、威力、伤害类型、元素和来源标记；输出护盾损失、生命损失、反应结果及能量变化。AI 预测和 UI 预览复用无副作用的计算部分。普攻、技能、追加伤害与持续伤害明确规则后都从该入口执行。

**验收**

无加成、单独增伤、单独减伤、两者并存、护盾、真伤、融化、追加伤害和轮次倍率分别有固定输入与预期输出。显示数值、事件数值和实际生命变化保持一致。

### P1-03：同一个可变 Buff 实例被加入两个角色

**位置**

- `scripts/character/pvz2_huojvshuzhuang.gd:51–64`。
- `scripts/buff/BuffManager.gd:13–39`。

**判断：确定逻辑问题。**

火炬树桩技能只创建一次 `add`，先把 `target` 设成 `player` 加入其管理器，再把同一个对象的 `target` 改成 `choice` 加入另一个管理器。管理器并没有复制实例。

两名角色因此可能共享目标指针、剩余时间和层数，移除时也可能对错误的目标减去属性。若允许选自己，还需要另行确认是否应该叠加。

**建议**

每个受益者创建自己的 Buff 实例；可共享只读定义，不共享运行时目标、持续时间和层数。把 source/target 的归属写成明确契约。

**验收**

A、B 各获得同名 Buff 后，移除或延长 A 的效果不会影响 B；双方属性最终回到各自正确值。

### P1-04：目标筛选结果没有贯穿选择流程

**位置**

- `scripts/fighting.gd:1322–1325`。
- `scripts/fighting.gd:1412–1443`，特别是第 1439 行。

**判断：确定逻辑问题。**

“没有可选目标”的判断只检查一到四号按钮，没有检查五号。只剩第五名可选时，会错误返回 `null`。

另一个 AI 选择函数已经计算出 `can_be_target`，最后却遍历完整 `enemy_team` 排序，可能重新选到刚刚排除的死亡角色或不允许选择的当前角色。

**建议**

先得到唯一的合法目标数组，UI、AI、无目标判定都使用该数组。不要手写五个按钮状态作为业务真相。目标选择结果应明确区分取消、无目标与有效目标。

**验收**

仅第五个目标合法；允许/禁止自己；允许/禁止死亡目标；全部无目标；选择取消，这些情形各测试一次。

### P1-05：寄生的“最多灌溉两次”未生效

**位置**

- `base/character_base.gd:297–301`。
- 项目机制说明中的寄生灌溉规则。

**判断：确定逻辑问题。**

判断了 `parasitism_watered_times < 2`，但成功灌溉后没有增加这个计数。代码其他位置能看到重置，未看到相应递增。

因此第三次及更多水伤仍可能继续乘以 1.5，而不是停止在两次增幅。

**建议**

仅在灌溉成功后递增；明确重新施加、覆盖、清除和到期时如何重置。

**验收**

同一寄生状态受第一、第二、第三次水伤时，仅前两次提高强度。重新施加是否重新获得两次机会由规则明确决定。

### P1-06：AI 评分会修改被评估数据，同时存在比例整数除法

**位置**

- `scripts/ai/fighting_ai.gd:307–323`：评分时累加 `skill.buff_value`。
- `scripts/ai/fighting_ai.gd:385–396`：评估某一技能时修改其他技能的 `value`。
- `scripts/ai/fighting_ai.gd:512、515`：两个整数生命值相除。
- `scripts/ai/fighting_ai.gd:369`：能量消耗比例，按实际技能字段类型核查整数除法。

**判断：确定存在副作用及生命比例计算错误；具体行动偏差需要运行场景确认。**

技能评分应回答“这个状态下，这个行动价值多少”，而不应修改技能定义或其他候选行动。当前写法让重复评分、候选遍历顺序及刷新时间有机会影响结果。

角色当前生命与最大生命均为整数，所以类似 `9000 / 10000` 的结果是 0，不是 0.9，换人时健康程度评分会失真。

**建议**

评分使用只读战斗快照和局部变量，返回分数及可选解释，不改变技能对象。比例显式转换到浮点数，例如 `float(curr_hp) / max_hp`，并处理分母合法性。先修确定性，再调启发式权重。

**验收**

对同一快照连续评分十次，分数、排序和输入对象都不变；交换候选顺序不改变每个行动自身的评分；90% 与 10% 生命的角色不会被当作同一比例。

## 四、随后处理的工程问题

### P2-01：技能描述、执行和 AI 预测有多份真相

`scripts/character/pvz2_huobaolajiao.gd:41、68`：执行伤害威力与 AI 中填写的威力分别为 3,000 和 4,000。
同文件第 23、52 行还能看到实际恢复能量与 AI 描述的数据差异。

应把可共享数据放入一个技能定义，由说明、执行和预测读取；复杂技能仍可以有专用逻辑，不必为了“数据驱动”把所有行为塞进一个万能函数。

### P2-02：Buff/AI 的 Node 生命周期不完整

`Buff` 与 `FightingAI` 都继承 `Node`；后者在角色基类通过 `.new()` 创建，Buff 也大量通过 `.new()` 创建。没有在这些实现中看到相应挂树或显式释放；管理器移除 Buff 主要是字典 `erase()`。

普通 `Node` 不是引用计数对象。仅擦除字典条目不等于释放节点。建议不需要场景树功能的数据对象采用 `RefCounted`，或明确将 Node 加入所有者子树并负责释放。重复 Buff 被拒绝的分支也应处理新建实例。

这是生命周期审查结论，不是已测得的内存增长量。

### P2-03：Buff 回调中删除正在遍历的字典

`BuffManager.gd:123–126` 直接遍历字典并执行回调；`huojvshuzhuang_skilla_mark.gd:18–22` 在回调中可能调用移除操作。

应对稳定键快照迭代并处理对象有效性，或者收集待执行变更在事件结束后统一应用；还要明确事件触发顺序。仅改成 `.keys()` 不自动解决所有嵌套移除问题。

### P2-04：一个 Buff 跳过更新会中断整个管理器

`BuffManager.gd:81–108` 中，第 90–93 行使用 `return`，不是跳过当前项的 `continue`。未来混合“双方回合更新”与“仅己方回合更新”的 Buff 时，结果可能受字典顺序影响。

这是扩展隐患；未据此断言当前所有对局都受影响。应明确持续时间的轮/回合单位、暂停规则及永久效果表示，不能简单把所有 `== 0` 改成 `<= 0`。

### P2-05：持续时间叠加只处理了 round_duration

`BuffManager.gd:22–28` 在重置/延长持续时间时只处理 `round_duration`。按回合持续的效果、新施法来源以及不同强度重施应如何处理，需要补充统一契约。

### P2-06：开局与入场效果的顺序需要统一

`fighting.gd:169–173` 先决定先手并触发相关信号，随后第 195–209 行才处理入场；活动角色标记也依赖后续刷新。若入场改变速度或状态，需要确定它对第一轮顺序是否生效。

第 196–201 行“大于”和“小于”速度分支都先执行玩家入场，和按速度处理的注释不符。建议由一次清晰初始化依次完成：生成队伍、设定活动者、应用入场、确定回合状态、更新展示。

### P2-07：结束状态、同时死亡与自毁条件需要边界测试

胜负处理应先归集该次行动所有伤害、追加和死亡，再依据明确规则作出唯一结果。当前按玩家/敌人分支先后检查，以及主要以 UI 展示表示结束的做法，需验证同时失去最后角色的情况。

部分技能用 `team.size()` 判断剩余角色，而死亡角色仍保留在队伍数组中；数组长度不等于存活数。应统一获得存活队伍成员的方法。

这部分未通过真实对局复现；不能据此断言一定会出现双重胜负弹窗。

## 五、不建议现在做的事

- 不因为主控制器 1,562 行就全部重写。长文件不是自动判错，但其中回合、UI、动画、换人和判死相互交叉已经造成具体问题，应按职责逐步迁移。
- 不立即换语言、换引擎、加入联机或复杂 AI 框架。
- 不用新增大量角色来替代完成已有玩法。
- 不为了“规范”一次性重命名所有文件、重做所有素材、建立过度抽象的框架。

## 六、建议的最小整理结构

保留现有角色继承、具体技能和已有 Buff 的设计成果，逐步明确：

1. `BattleFlow`：当前状态、行动合法性、回合推进、换人、死亡及结束。
2. `DamageResolver`：唯一数值计算与结算结果；可单独测试。
3. `BattleUI`：展示状态、收集输入、播放动画；不直接决定能否行动。
4. `SkillDefinition`：描述、费用、基础威力等可共享定义。
5. 现有 Character / Buff / AI：在以上契约下工作，不直接相互改写临时 UI 状态。

这些是职责建议，不要求马上新建五个大类。最小第一步是统一行动入口和伤害入口。

## 七、继续开发的三个验收里程碑

### 里程碑 A：一场战斗不会被输入和状态打断

完成 P1 修复；覆盖连点、非己方输入、能量不足、取消选人、最后合法目标、死亡换人和战斗结束后的输入。没有通过这些验证前，不增加复杂技能。

### 里程碑 B：别人能够独立完成并重复一局

从已有角色中选 6–8 个作为重点平衡样本，不删除其余成果。完成一个模式的说明、组队或合理预设、完整对局、胜负和再次开始。让玩家看得见能量成本、关键 Buff、剩余持续时间与实际伤害反馈。

若目标只是单局战斗游戏，不需要为了“完整”强加养成、开放世界或剧情系统。

### 里程碑 C：验证是否真的有值得重复玩的决策

建议邀请 5–10 名未参与开发的人测试，这是建议的测试规模，不是现有测试结果。
观察他们是否能够独立操作、解释一两次关键输赢原因、发现不同队伍的玩法差异，以及是否主动愿意再开一局。

“角色熟悉所以愿意点开”和“决策有趣所以愿意重玩”是不同证据。源码能证明实现过机制，不能证明这些机制已经好玩。

## 八、公开或商业发行前的素材问题

项目角色与素材明显涉及已有作品。上传包本身不能证明是否拥有相应许可，本评审也没有核实授权。

不要把“免费同人”自动理解为能够公开发行。EA 官方内容政策并未把一般个人内容许可扩展为任意同人游戏许可，并明确限制 fan games 等使用。其他作品、音乐、字体、图像的许可也应分别核对。

## 九、给作者的评价

- 一次行动只结算一次。
- 一个效果只属于正确的对象。
- 同一组数据只有一个可信来源。

- 新功能加入后，旧机制有测试保护。
